# FLS-AI-013 — Short-term structured conversation context

## Architecture / API

Existing POST /api/ai/chat remains stateless for old callers. Customer widget opts in:

```json
{"message":"Tìm hoa dưới 1 triệu","memory":true}
```

Response preserves reply/type/products and adds conversationId only after successful persistence.
Follow-up request:

```json
{"message":"Có màu hồng không?","conversationId":"<64 lowercase hex characters>"}
```

memory must be boolean when supplied; conversationId must be a 256-bit opaque ID generated by
Node crypto.randomBytes(32). The client cannot supply context/history, roles, product snapshots
or raw MongoDB filters. Unknown/expired/wrong-owner IDs yield a new empty conversation with a
new random ID; no existence or ownership information is returned.

## Persistence and ownership

New Mongoose AIConversation collection (aiconversations): string _id, owner (authenticated
customer ID or null for guest), constraints, productIds, selectedId, revision, expiresAt,
createdAt/updatedAt. No changes to Product/Order/SupportRequest schemas. No dependency added.
Mongo persistence survives Render restarts; there is no in-process memory dependency.

TTL is 30 minutes since the last successful save. expiresAt has expireAfterSeconds:0 TTL index.
Reads and updates also enforce expiresAt > now, independent of asynchronous Mongo TTL deletion.
Mongoose declares the new collection/index; actual Atlas index creation/cleanup was not verified
in this session. Existing records/collections require no migration or backfill.

Customer identity comes from existing verified JWT and active account lookup; every read/update
filters by owner. Guest IDs are bearer capabilities: an unguessable ID is needed to resume that
guest context, and must not be shared/logged. Guests never resume account-owned contexts and
accounts never automatically adopt guest contexts. No context read/list endpoint is exposed.

Widget stores only ID + UI account scope in sessionStorage. Scope decoded on the client is
used only to avoid reusing an ID after login/account switch; it is never backend authorization.
Refresh in the same tab restores context. Independent tabs normally start independent contexts;
browser duplicate-tab can copy sessionStorage. Concurrent updates to a shared ID use revision
compare-and-set; a stale write returns 409 CONVERSATION_CONFLICT, allowing a manual retry.

## Limits / privacy / Groq

Structured memory only: up to six text constraints (keyword/occasion/color/recipient/style/flower,
each search term bounded to 200 characters), two price bounds, last four search-result product IDs,
and one selected product ID. No raw recentMessages, free-text assistant transcript, product name,
price/stock snapshot, order/payment/voucher/support status or human transcript is stored.

This intentionally uses zero historical messages in Groq calls. Provider receives only its fixed
system instruction and the current user message, sanitized with the existing safeMessage helper.
No history can become a system instruction; the model never constructs executable search filters.
Keyword memory reuses the same sanitizer. Arbitrary unmarked sensitive free text is not perfectly
detectable: users should not submit it. No new PII extractor or long-term profile was introduced.

## Follow-ups and fresh products

ConversationIntent reuses ProductSearchIntent for budget validation. Explicit new budget removes
the previous price bounds before applying the new ones. New color/recipient/flower overwrites
the corresponding prior constraint. “Rẻ hơn” reduces the previous upper budget by 20%, explicitly
stated in the response; without an upper budget it asks for a number. “Loại khác” excludes the
last four IDs before the bounded database search.

ProductDAO.searchForAssistant accepts two extra validated tool parameters: keywords (1–6 literal
terms combined with AND across existing name/description/category/submenu fields) and excludeIds
(at most four valid ObjectIds). Existing keyword/API behavior is unchanged. No color/occasion/
recipient product fields were invented. Missing descriptive data means no matching results;
this grammar does not infer suitability from undocumented attributes or perform semantic search.

“Mẫu đầu tiên”, “mẫu thứ N”, “mẫu cuối” use the last search-result ID ordering. “Cái đó” or
“mẫu vừa rồi” uses the explicitly selected ID or the sole last result, otherwise asks clarification.
ProductSearchTool.getProduct reuses ProductDAO.selectByID and projects public fields afresh on
every reference question. Out-of-stock references explicitly report current stock=0; deleted or
incomplete products report unavailable. Recommendations still exclude stock<=0. No price/stock
from memory or Groq is used. The retained search-result ordering is separate from a single-product
detail reply; subsequent “cái đó” refers to the selected detail product.

## Human support / failure behavior

Opted-in requests pause for pending and in_progress support; guards run before and after AI work.
Existing legacy active guard remains. Support data is fetched live, never taken from memory.
On load, a later SupportRequest creation invalidates older account conversation context, including
old IDs from another tab after resolution. UI clears its ID on handoff and returns with clean AI
context after resolution. It remembers the last ended support ID so repeatedly opening/refeshing
an already-ended session does not keep erasing new AI context. Human transcripts never enter Groq.

“Trò chuyện mới” clears the tab ID, displayed AI messages and handoff draft. It does not delete
SupportRequest data. Old memory expires through TTL. Minimize does not reset the conversation.

Load/save failure returns 503 CONVERSATION_UNAVAILABLE and no fake memory success. Invalid ID
returns 400. Groq failure never calls save; existing context stays unchanged. Read/write conflicts
return 409. Database/provider raw errors and stack traces are not returned.
